Your chatbot answers questions using a knowledge base built from your training data. The better your training data, the better the responses.

## Data sources

| Source | Best for | Endpoint |
|--------|----------|----------|
| **Text** | FAQs, Q&A pairs, short content | [`POST /training/text`](/api-reference/training-text) |
| **URLs** | Documentation, blog posts, help articles | [`POST /training/urls`](/api-reference/training-urls) |
| **Files** | PDFs, CSVs, JSON, TXT documents | [`POST /training/files`](/api-reference/training-files) |

## Async processing

All training is **asynchronous** and queue-based. Every training endpoint returns `202 Accepted` immediately with a `session_id`:

```json
{
  "session_id": "txt_a1b2c3d4e5f6",
  "chatbot_id": "cb_123",
  "status": "queued",
  "message": "Training queued for background processing",
  "data_source_ids": ["ds_abc123"]
}
```

Tasks are processed by background workers. Poll the status endpoint to track progress.

## Processing pipeline

After uploading:

1. Content is queued for processing
2. Text is extracted and cleaned
3. Content is split into chunks using your chosen strategy
4. Each chunk is embedded as a vector (OpenAI embeddings)
5. Vectors are stored in the knowledge base (Qdrant)

## Deduplication

All training endpoints automatically deduplicate content using SHA-256 hashes:

- **Text**: Hashes the content string
- **URLs**: Hashes the URL string
- **Files**: Hashes the raw file bytes

If identical content was already uploaded to the same chatbot and is **pending**, **processing**, or **completed**, the duplicate is skipped. Failed data sources do **not** block re-upload, so you can retry after fixing issues.

When all items in a request are duplicates, the response is `200` with `"status": "duplicate"` instead of `202`. Partial duplicates still return `202` — duplicate items appear in the `rejected_files` array.

A `training.duplicate` webhook fires when duplicates are detected, so your integration isn't left waiting for a `training.completed` that never comes.

## Concurrency limits

| Limit | Value |
|-------|-------|
| Per user | Up to **5 files** process concurrently |
| System-wide | Up to **30 concurrent** AI chunking operations |

Additional requests are processed immediately via async tasks. No global queue — each upload fires directly.

### Parallel training example

Send multiple requests in parallel. They queue and process concurrently:

```python
import requests, time, concurrent.futures

api_key = "ak_live_YOUR_KEY"
bot_id = "cb_YOUR_BOT_ID"
headers = {"X-API-Key": api_key, "Content-Type": "application/json"}

# 1. Fire off multiple training requests (all return 202 instantly)
def train_doc(doc):
    resp = requests.post(
        f"https://api.cleveract.ai/v1/chatbots/{bot_id}/training/text",
        headers=headers,
        json={"title": doc["title"], "content": doc["content"]}
    )
    return resp.json()

documents = [
    {"title": "FAQ", "content": "Q: Pricing?\nA: $29/month."},
    {"title": "Setup Guide", "content": "Step 1: Create account..."},
    {"title": "API Docs", "content": "Authentication uses X-API-Key header..."},
]

with concurrent.futures.ThreadPoolExecutor(max_workers=5) as pool:
    results = list(pool.map(train_doc, documents))
    print(f"Queued {len(results)} tasks")

# 2. Poll until all done
while True:
    status = requests.get(
        f"https://api.cleveract.ai/v1/chatbots/{bot_id}/training/status",
        headers=headers
    ).json()
    print(f"Pending: {status['pending']}, Processing: {status['processing']}, Completed: {status['completed']}")
    if not status["is_active"] and status["pending"] == 0 and status["processing"] == 0:
        break
    time.sleep(2)

print("All training complete!")
```

## Chunking strategies

When you upload content, it gets split into **chunks** -- small searchable segments the AI retrieves when answering.

| Strategy | Description | Best for |
|----------|-------------|----------|
| `auto` | AI picks the best strategy | Most use cases (recommended) |
| `individual` | One chunk per item/row | FAQs, CSV rows, structured data |
| `semantic_groups` | Groups related content | Long documents, manuals |

```bash
curl -X POST https://api.cleveract.ai/v1/chatbots/bot_abc/training/text \
  -H "X-API-Key: ak_live_YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Product FAQ",
    "content": "Q: What is CleverAct AI?\nA: An AI chatbot platform.\n\nQ: How much?\nA: Plans start at $29/month.",
    "chunking_strategy": "individual"
  }'
```

## Metadata schema

Define metadata fields on your chatbot to control how AI extracts and structures data from training content. The schema tells the AI what fields to look for, how to type them, and how to use them during search.

### Define fields via API

```bash
curl -X PUT https://api.cleveract.ai/v1/chatbots/{chatbot_id} \
  -H "X-API-Key: ak_live_YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "metadata_schema": {
      "fields": [
        {
          "name": "date",
          "type": "date",
          "description": "Recording date in YYYY-MM-DD format",
          "filterable": true,
          "include_in_chunk": false
        },
        {
          "name": "speaker_label",
          "type": "text",
          "description": "Which speaker said this utterance (e.g. Speaker A, Speaker B)",
          "filterable": false,
          "include_in_chunk": true
        },
        {
          "name": "timestamps",
          "type": "text",
          "description": "Time range in HH:MM:SS to HH:MM:SS format",
          "filterable": false,
          "include_in_chunk": true
        },
        {
          "name": "category",
          "type": "select",
          "description": "Content category",
          "filterable": true,
          "include_in_chunk": false,
          "options": ["meeting", "lecture", "interview"]
        }
      ]
    }
  }'
```

### Field properties

| Property | Type | Description |
|----------|------|-------------|
| `name` | string | Field name (used as key in metadata) |
| `type` | string | `text`, `number`, `date`, `boolean`, `tags`, `select` |
| `description` | string | Tells the AI what this field is and how to extract it |
| `filterable` | boolean | When `true`, the agent can filter search results by this field before semantic search |
| `include_in_chunk` | boolean | When `true`, this field's data is always included in the chunk text — never dropped |
| `options` | string[] | For `select` type — valid values |

### Filterable fields

When a field is `filterable: true`, your agent can narrow search results before doing semantic search. For example, if `date` is filterable and a user asks "What did we discuss last week?", the agent filters to recent dates first, then searches within those results.

### Include in chunk

When a field is `include_in_chunk: true`, the AI always preserves that field's data in the chunk text. This is important for structured content like transcripts — without it, the AI might sometimes drop timestamps or speaker labels from the chunk text.

**Example:** A meeting transcript with `timestamps` and `speaker_label` set to `include_in_chunk: true` will always produce chunks like:

```
Speaker A (00:00:02 to 00:00:07): I wanted to start by going over the progress...
Speaker B (00:00:07 to 00:00:17): The engineering team has completed the backend...
```

Without `include_in_chunk`, the AI might inconsistently format chunks — sometimes including timestamps, sometimes dropping them.

## Custom metadata

Tag training data with per-request metadata for filtering at query time:

```bash
curl -X POST https://api.cleveract.ai/v1/chatbots/{id}/training/text \
  -H "X-API-Key: ak_live_YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Alice Knowledge Base",
    "content": "Your content here...",
    "custom_metadata": {
      "user_id": "alice",
      "category": "onboarding"
    }
  }'
```

<Note>
  **Metadata schema vs custom_metadata**: The schema (set on the chatbot) defines what fields the AI extracts automatically from content. `custom_metadata` (sent per request) adds static tags you already know — like `user_id` or `category`. Both end up in the chunk metadata and can be used for filtering.
</Note>

See the [Multi-User Isolation](/guides/multi-user-isolation) guide for how metadata enables per-user data filtering.

### Updating metadata

You can update metadata on existing data sources without re-uploading. New keys are added, existing keys are overwritten:

```bash
curl -X PATCH https://api.cleveract.ai/v1/data-sources/{data_source_id} \
  -H "X-API-Key: ak_live_YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "custom_metadata": {
      "category": "billing",
      "language": "en"
    }
  }'
```

Changes sync to the vector store automatically, so search filters reflect the update immediately. See the [API reference](/api-reference/data-sources-update) for full details.

## Tips for good training data

<AccordionGroup>
  <Accordion title="Structure your FAQs clearly">
    Use `Q:` and `A:` prefixes, or CSV format with `question` and `answer` columns. The `individual` chunking strategy works best.
  </Accordion>
  <Accordion title="Keep content focused">
    Each training source should cover one topic. Multiple focused sources > one giant document.
  </Accordion>
  <Accordion title="Include variations">
    People ask the same question in different ways. Include common phrasings in your training data.
  </Accordion>
  <Accordion title="Update regularly">
    Delete outdated sources and upload fresh content. Stale data leads to wrong answers.
  </Accordion>
</AccordionGroup>

| Limit | Value |
